# ADR-001: Outbox transaccional para notificar webhooks sin perder eventos

- Estado: aceptada
- Contexto del requisito: "por cada evento aceptado, enviar un POST al webhook del tenant; el
  envio no bloquea la respuesta del registro; reintentar hasta 5 veces; sin perder eventos".

## Contexto

Aceptar un evento implica dos efectos: guardarlo en PostgreSQL y avisar al cliente por HTTP.
No se pueden hacer atomicos (PostgreSQL y el servidor del cliente no comparten transaccion),
asi que hay que decidir que falla primero y como se recupera. Ademas el envio puede tardar
hasta 5 s por intento y reintentarse durante minutos: no puede ocurrir dentro de la peticion.

## Decision

Se usa el patron **outbox transaccional**:

1. `RegistrarEvento` inserta el evento, actualiza la guia e inserta una fila `PENDIENTE` en
   `notificaciones` **en la misma transaccion**. O existen las tres cosas o ninguna.
2. Un worker (`NotificacionWorker` + `DespacharNotificaciones`) lee las notificaciones vencidas,
   las reclama con `FOR UPDATE SKIP LOCKED` y un arrendamiento (`bloqueada_hasta`), hace el
   POST **fuera de cualquier transaccion** y registra el resultado: `ENVIADA`, reprogramada con
   espera exponencial con jitter, o `FALLIDA` tras el quinto intento.
3. Garantia de entrega: **al menos una vez**. El payload y la cabecera `X-Event-Id` permiten al
   cliente deduplicar.

La tabla `notificaciones` tiene `UNIQUE (tenant_id, event_id)`: incluso un error de aplicacion
no puede crear dos notificaciones para el mismo evento.

## Alternativas descartadas

| Alternativa                                                  | Por que no                                                                                                                                                                                                                                     |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lanzar el POST en memoria tras el `COMMIT` (fire-and-forget) | Si el proceso muere entre el commit y el envio, la notificacion se pierde y nadie lo sabe. Incumple "sin perder eventos".                                                                                                                      |
| Enviar dentro de la peticion / de la transaccion             | Bloquea la respuesta hasta 5 s por intento y mantiene una transaccion y una conexion abiertas mientras se espera a un tercero. Incumple "no bloquea".                                                                                          |
| Cola externa (Redis, RabbitMQ, SQS)                          | Reintroduce el problema de doble escritura (guardar en BD y publicar en la cola) y obliga a operar otra pieza de infraestructura. Con el volumen del problema, PostgreSQL ya da durabilidad, consulta de fallidas por SQL y transaccionalidad. |
| `LISTEN/NOTIFY` o CDC (Debezium) como disparador             | Reducen la latencia, pero anaden complejidad; el sondeo de 1 s cumple "casi en tiempo real". Se puede anadir `NOTIFY` encima sin cambiar el modelo.                                                                                            |

## Consecuencias

Positivas:

- Un reinicio, un fallo del webhook o una caida del worker no pierden notificaciones: el estado
  esta en la base de datos y el arrendamiento expirado devuelve la fila a la cola.
- Varias instancias pueden despachar a la vez sin duplicar trabajo (`SKIP LOCKED`).
- Las notificaciones fallidas quedan consultables (`GET /notificaciones?estado=FALLIDA`).
- El dominio no conoce HTTP ni colas: `Notificacion` solo decide entre reprogramar o fallar; el
  envio es el puerto `WebhookSender`.

Negativas y mitigaciones:

- **Entrega al menos una vez**: si el proceso muere despues de que el cliente respondio y antes
  de guardar el resultado, el evento se reenvia. Mitigacion: `X-Event-Id` estable.
- **Sin orden garantizado** entre eventos de una misma guia cuando hay reintentos (el evento 2
  puede llegar antes que el 1 si el 1 fallo). Mitigacion: el payload lleva `fechaEvento`.
  Garantizar el orden exigiria bloquear la cola por guia; queda como mejora.
- **Latencia de hasta `WORKER_POLL_INTERVAL_MS`** (1 s por defecto) en la primera entrega.
- Sondeo constante a la base de datos: el indice parcial sobre `PENDIENTE` mantiene la consulta
  barata. Los relojes de las instancias deben estar razonablemente sincronizados.
